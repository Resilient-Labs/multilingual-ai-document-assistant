## `components/upload-form.tsx` — findings

### 🔴 High — WCAG 2.1 **4.1.3 Status Messages** (and related **4.1.2 Name, Role, Value**)

**Issue:** While `isSubmitting` is true, the submit control renders only `<Spinner />`. `submitLabel` is computed to include `ocrProgress` (e.g. “Recognizing… 50%”, “Uploading…”) but that string is **not** rendered when the spinner is shown. `Spinner` uses a fixed `aria-label="Loading"` and does not reflect changing progress.

**Impact:** Screen reader users do not receive programmatic updates as OCR/upload state changes during a long operation.

**Fix pattern:**

- Render progress text for everyone or expose it to AT only, e.g. show `{submitLabel}` beside the spinner, **or** add a visually hidden live region:

```tsx
{isSubmitting && ocrProgress ? (
  <span className="sr-only" aria-live="polite" aria-atomic="true">
    {ocrProgress}
  </span>
) : null}
```

- And/or set `aria-busy="true"` on the `<form>` while submitting and keep the submit button’s accessible name in sync, e.g. `aria-label={isSubmitting ? (ocrProgress ?? "Translating document") : undefined}` on the submit `Button` (in addition to visible content).

---

### 🟡 Medium — WCAG 2.1 **2.4.3 Focus Order** / **4.1.2** (nested interactive controls)

**Issue:** The dropzone root from `getRootProps()` is keyboard-focusable (`tabIndex={0}` from `react-dropzone`). Inside it, **mobile** renders a `Button` (“Take photo”) and **desktop** renders a `Button` (“Browse files”). That yields **multiple tab stops** and nested interactive elements for one logical “choose file” control.

**Impact:** Extra tab stops, possible confusion for keyboard and screen reader users; events may not align with `react-dropzone`’s `onKeyDown` guard (which expects the root as `event.target`).

**Fix pattern:**

- Prefer a **single** primary control: e.g. use `useDropzone`’s `open` with one visible `<button type="button">` that calls `open()`, and set `noClick: true` on the root if the root should not be a second button; **or** replace inner `Button` with non-focusable styled elements (`<span>` / `<p>`) so only the root receives focus.

---

### 🟡 Medium — WCAG 2.1 **1.3.1 Info and Relationships** / **4.1.2** (custom file control naming)

**Issue:** The file input is visually hidden (`getInputProps()`). Visible headings (“Take a photo or upload a file”, “Drag & drop…”) are not tied to the control with `aria-labelledby` / `aria-describedby`, and `getRootProps()` is not given an explicit accessible name.

**Impact:** Some AT may announce the focusable dropzone root only as a generic focusable region unless the user reads surrounding static text.

**Fix pattern:**

```tsx
<div
  {...getRootProps({
    "aria-label": "Upload document: PDF, Word, text, or image, up to " + maxSizeLabel,
  })}
>
```

**Or** add `id` to the visible title `<p>` and pass `aria-labelledby` that id into `getRootProps({ "aria-labelledby": "upload-heading" })`.

---

### 🟡 Medium — WCAG 2.1 **1.1.1 Non-text Content** (decorative icons)

**Issue:** `FileTextIcon` and `UploadCloudIcon` sit next to or above text that already conveys the same information. They lack `aria-hidden="true"`, so they may be exposed as redundant graphics in the accessibility tree.

**Fix pattern:**

```tsx
<FileTextIcon className="..." aria-hidden="true" />
<UploadCloudIcon className="size-16 text-indigo-400" aria-hidden="true" />
```

(Keep `aria-label` on true icon-only controls like “Remove file” and “Swap languages” — those are already correct.)

---

### 🔵 Low — WCAG 2.1 **1.4.3 Contrast (Minimum)**

**Issue:** `text-indigo-600` on `bg-indigo-100` / `bg-indigo-200` for hints (“Tap to replace”, “Click or drag to replace”) may be below 4.5:1 depending on exact palette tokens.

**Fix pattern:** Verify with a contrast checker; if failing, use a darker text token (e.g. foreground on muted) or stronger background from the design system.

---

### 🔵 Low — WCAG 2.1 **3.3.1 Error Identification** (enhancement)

**Issue:** Global `role="alert"` + `aria-live="assertive"` correctly surfaces `error`. The hidden file input does not use `aria-describedby` pointing at the alert id.

**Fix pattern:** When `error` is set, set `aria-invalid` on the relevant control and `aria-describedby` to the error element’s `id` (requires stable `id` on the alert container).

---

### Positive notes (no change required)

- Swap and remove-file controls use real `<button>` with `aria-label`.
- Form uses semantic `<form>` and submit `Button` with `type="submit"`.
- Error container uses `role="alert"` and `aria-live="assertive"`.
- `Spinner` exposes `role="status"` and a loading label (static only — see High finding).
- Project `Button` uses `focus-visible` ring, not bare `outline: none` without replacement.
