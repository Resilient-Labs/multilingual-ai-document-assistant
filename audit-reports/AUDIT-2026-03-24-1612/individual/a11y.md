# Accessibility audit — Q&A chat UI

**Scope:** `components/features/document/QAPanel.tsx` (primary), `app/api/ask/route.ts` (context only)  
**Standard:** WCAG 2.1 Level AA  
**Date:** 2026-03-24

---

## Executive summary

`QAPanel` uses a real `<form>`, native `<input>` and `<button>`, `aria-label` on the icon-only submit control and the text field, destructive `Alert` for errors, and visible loading copy (“Thinking…”) plus spinners with accessible names. The main gaps are **semantic structure** of the conversation (headings, message roles/labels) and **dynamic updates** for assistive technologies (live regions / busy state), plus a few **best-practice** polish items (decorative icons, focus behavior).

`app/api/ask/route.ts` has **no user-facing accessibility surface**; it only streams or returns JSON. No WCAG issues apply to the route itself.

| Level | Meaning |

## Findings

### 1. Conversation panel lacks landmark and heading semantics

**Severity:** Medium  
**WCAG:** 1.3.1 Info and Relationships, 2.4.6 Headings and Labels (headings), 1.3.2 Meaningful Sequence (related)

The panel uses `Card` / `CardHeader` / `CardTitle` (“Document Q&amp;A”). In this codebase, `CardTitle` renders a `<div>`, not a heading (`h2`–`h6`). Screen reader users lose a navigable outline entry for this panel.

**Fix pattern:**

- Give the panel title a real heading, e.g. render `CardTitle` as `<h2 className={...}>` (or wrap the string in `<h2>` with the same styles), scoped to an appropriate level for the page.
- Optionally wrap the chat column in `<section aria-labelledby="qa-panel-title">` or `role="region"` with `aria-label="Document Q&amp;A"` if the page doesn’t already provide a landmark.

---

### 2. Chat messages are plain `<div>`s without “who spoke” semantics

**Severity:** Medium  
**WCAG:** 1.3.1 Info and Relationships

Each message is a `div` with alignment and color classes. Sighted users infer user vs assistant from placement and styling; **screen reader users** get sequential text without an explicit “You” / “Assistant” (or similar) label unless they infer from layout (which is not reliable for all AT).

**Fix pattern (choose one or combine):**

- Wrap each message in a container with `aria-label` describing the speaker, e.g. `aria-label="Assistant message"` / `aria-label="Your message"`, or
- Prefix visually hidden text: `<span className="sr-only">Assistant: </span>` before bubble content, or
- Use `role="article"` with `aria-labelledby` / `aria-label` per bubble.

Ensure the order in the DOM matches the conversation order (it already does).

---

### 3. No live region for new or streaming assistant content

**Severity:** Medium  
**WCAG:** 4.1.3 Status Messages (where applicable); general robustness for dynamic content

New assistant text appears as streams or replacements in the DOM. Without `aria-live` (typically `polite`) or a dedicated status pattern, **some screen readers may not announce** when the answer starts or finishes, depending on focus and navigation mode.

**Fix pattern:**

- On a wrapper around the message list (or assistant messages only), add `aria-live="polite"` and `aria-relevant="additions text"` (tune as needed to avoid excessive chatter during token streaming).
- During loading, consider `aria-busy="true"` on that region or a dedicated “status” line, cleared when the response completes.
- For streaming, some teams use a **single** live region for “assistant output” and update it carefully to balance verbosity vs feedback.

---

### 4. “Thinking…” row: good text; spinner + status role interaction

**Severity:** Low  
**WCAG:** 4.1.2 Name, Role, Value (minor duplication)

The loading row includes visible text “Thinking…” and a `Spinner` that uses `role="status"` and an `aria-label`. That can be redundant or noisy depending on the browser/AT combination.

**Fix pattern:**

- Prefer one primary announcement: e.g. keep visible “Thinking…” and mark the spinner decorative with `aria-hidden="true"` on the spinner when adjacent text is present, **or** keep the spinner as the only named status control and use visually hidden text instead of visible duplicate semantics.

---

### 5. Icon-only send button: decorative SVG

**Severity:** Low  
**WCAG:** 1.1.1 Non-text Content (decorative), 4.1.2 (avoid redundant name)

The submit `Button` has `aria-label="Send question"`. The `SendHorizontal` icon should be **decorative** so AT doesn’t try to expose an unnamed icon inside an already labeled button.

**Fix pattern:**

```tsx
<SendHorizontal className="size-4" aria-hidden="true" focusable="false" />
```

(`focusable="false"` helps older SVG cases; Lucide typically sets this appropriately.)

---

### 6. Scroll sentinel `div` (auto-scroll anchor)

**Severity:** Low  
**WCAG:** 4.1.2 (minor; avoids stray “empty” announcements in some edge cases)

The empty `<div ref={bottomRef} />` is for `scrollIntoView`. It is not interactive; marking it inert to accessibility tree reduces noise.

**Fix pattern:**

```tsx
<div ref={bottomRef} aria-hidden="true" />
```

---

### 7. Input labeling: `aria-label` without visible `<label>`

**Severity:** Low (acceptable if purpose is clear in context)

The field uses `placeholder` and `aria-label="Question input"`. That satisfies programmatic naming; a **visible** label is still preferable for cognitive and low-vision users who rely on persistent text, not only placeholder.

**Fix pattern:**

- Add `<Label htmlFor="qa-input">` (or similar) tied to `id` on `Input`, and optionally keep `aria-label` aligned or rely on the visible label alone.

---

### 8. Focus management after submit / on new messages

**Severity:** Low

After send, focus typically remains on the input (good). When long answers stream, some teams move focus to the answer region or use `aria-live` instead; neither is strictly required by WCAG but improves predictability.

**Fix pattern:**

- Optional: after successful submit, move focus to the new assistant message container or announce via live region (coordinate with finding #3).

---

### 9. Color and contrast (user vs assistant bubbles)

**Severity:** Informational / verify in design review

User bubbles use `bg-primary text-primary-foreground`; assistant uses `bg-muted text-foreground`. **Contrast depends on theme tokens**; no hardcoded hex in this file. Validate **4.5:1** for normal text in both themes (light/dark) if not already covered by your design system.

**Fix pattern:** If any pair fails, adjust token values or add borders/patterns per 1.4.3 Contrast (Minimum).

---

## Positive observations

- **Native controls:** `<form>`, `type="submit"`, and disabled states align with keyboard and AT expectations.
- **Icon button:** `aria-label="Send question"` on the submit control (required for icon-only).
- **Text field:** Programmatic name via `aria-label` (not placeholder-only).
- **Errors:** `Alert` uses `role="alert"` (also set by the shared `Alert` component); errors are textual, not color-only.
- **Loading:** Visible “Thinking…” plus non-empty `aria-label` on spinners where used alone.
- **Focus styles:** Inherited `Button` / `Input` / `ScrollArea` styles use `focus-visible` ring patterns (from shared UI), not `outline: none` without replacement.

---

## `app/api/ask/route.ts`

- **No UI, no DOM, no WCAG applicability** for end-user accessibility.
- Error responses are JSON; any accessible error presentation is the **client’s** responsibility (`QAPanel` already surfaces `error.message` in an alert).
